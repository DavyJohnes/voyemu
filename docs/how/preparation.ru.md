# Подготовка

Подготовка превращает [профиль](profiles-machines.ru.md) и его оригиналы в машину тремя командами: `deps` устанавливает закреплённые инструменты, `fetch` импортирует и проверяет оригиналы, `build` подготавливает машину. Каждый шаг сверяет [пины](../why/pins.ru.md) того, что использует, и останавливается при расхождении.

```sh
./voyemu deps free-09-chinese-20260106-6.0.3
./voyemu fetch free-09-chinese-20260106-6.0.3 --source=path/to/update.zip
./voyemu build free-09-chinese-20260106-6.0.3
```

Лаунчер запускается из корня установки; на Windows это `voyemu.exe`. В корне установки лежат лаунчер и `profiles/`; для подготовки по умолчанию `src/` не нужен, см. [релиз](../dev/release.ru.md#файлы-проекта). Лаунчер берут из архива релиза или собирают из исходников в корне проекта, см. [сборку](../dev/build.ru.md). Для подготовки машины с QNX нужен лаунчер, собранный с графическим обработчиком; он есть в архивах релиза.

Путь к файлу или каталогу в опции, например `--source=update.zip`, может быть относительным от текущего каталога или начинаться с `~/` от домашнего каталога; символические ссылки в нём раскрываются. Перед использованием Voyemu переводит такой путь в абсолютный.

## deps

`deps [PROFILE]` устанавливает закреплённые инструменты хоста в `.local/toolchains/`: Android Emulator, Platform Tools, Build Tools, CMake и Ninja из SDK и движок QEMU для QNX. С профилем команда ещё подготавливает базу Android этого профиля, если она ему нужна. Кроме того, `deps` устанавливает JAR платформы Android и инструменты Java для подготовки, которые собирает и публикует CI: минимальную среду Java хоста, помощник на Java и гостевой код Java профилей, см. [CI](../dev/ci.ru.md). JDK не нужен; почему — в [подготовке на Java](../why/java-preparation.ru.md). По умолчанию закреплённый ресурс помощника используется даже в рабочей копии исходников. Если он недоступен, подготовка завершается с `JAVA_HELPER_ASSET_MISSING`; разработчик может явно выбрать рецепт из исходников через `--jdk`, см. [CI помощника Java](../dev/ci.ru.md#рабочий-процесс-java-helper).

Загрузки идут через HTTPS и хранилище сертификатов хоста: WinHTTP на Windows, libcurl на macOS и Linux. На Linux у Voyemu нет своего TLS и своей криптографии: он загружает системный libcurl (`libcurl.so.4`) для загрузок и OpenSSL 3 (`libcrypto.so.3`) для подписи APK в `build` и останавливается с `DOWNLOAD_LIBRARY` или `APK_CRYPTO_LIBRARY`, называя отсутствующую библиотеку. Если сервер отвечает HTTP 429 или 503, Voyemu повторяет запрос после задержки из `Retry-After` (не больше пяти минут) или после паузы от 2 до 64 секунд — всего до семи попыток. Уже скачанные файлы остаются в кеше, поэтому повторная команда продолжает с места остановки.

В stderr каждая команда называет каждую загрузку с её размером и хостом источника, показывает полученные байты, процент, скорость и оставшееся время и сообщает о каждой распаковке и о каждом шаге, который уже был установлен. В терминале одна строка состояния обновляется на месте; в остальном выводе строка состояния появляется на каждых следующих 10% или после 30 секунд без неё. Пустая строка отделяет каждую загрузку и каждый шаг, а размеры, скорость и время следуют языку вывода команд. Передача завершается ошибкой после 60 секунд без полученного байта, сколько бы она ни длилась в целом. Ошибка загрузки сообщает, что хост недоступен, передача остановилась, сервер ответил кодом HTTP или файл не совпадает с пином; `--offline` без файла в кеше называет этот файл. `deps` и `fetch` требуют на томе корня установки размер каждой загрузки или распаковки плюс 2 ГиБ свободного места, а `build` оставляет свободными 20 ГиБ для подготовки машины. Если места мало, ошибка называет свободное и нужное место в целых ГиБ, сколько освободить и корень установки, который можно перенести на другой диск, см. [корень установки](../dev/release.ru.md#корень-установки).

`build` проверяет холодный старт каждого подготовленного гостя без ограничения времени: ждёт первого кадра приборки и загрузки Android, раз в минуту сообщает прошедшее время и завершается ошибкой, если процесс гостя завершился.

Записи каждой команды, в том числе проверки холодного старта, попадают в её [лог команды](logs.ru.md#лог-команды), путь к которому выводит неудачная или прерванная команда; `--verbose` показывает их и в stderr.

Пока пин `prebuilt` движка QNX не опубликован, `deps` собирает движок по его рецепту, см. [рабочий процесс qnx-host](../dev/ci.ru.md#рабочий-процесс-qnx-host): на macOS — с Clang и `/usr/bin/python3` 3.9 или новее из Command Line Tools (их устанавливает `xcode-select --install`) и с Ninja из пакета CMake в SDK; на Linux — с закреплённым Zig, `/usr/bin/python3` 3.9 или новее, `/usr/bin/make` и Ninja из пакета CMake в SDK. На Windows `deps` устанавливает движок только из опубликованного ресурса или проверенного готового движка из локального кеша; иначе сообщает, что движок недоступен, и машины работают без приборки. `deps` повторно использует установленный движок того же рецепта. На Windows `build` форматирует образ кеша машины через `mke2fs.exe` и `mke2fs.conf` из Platform Tools, и подготовленная машина содержит отформатированный `cache.img`.

`--jdk PATH` запускает подготовку на JDK 25 или новее вместо среды Java и позволяет компилировать гостевой код Java профиля. В рабочей копии исходников эта опция также выбирает рецепт помощника для разработчика.

## fetch

`fetch PROFILE` импортирует или проверяет оригиналы профиля в `.local/profiles/<profile>/`.

| Форма | Действие |
| --- | --- |
| `fetch PROFILE` | Проверяет оригиналы, уже сохранённые для профиля |
| `fetch PROFILE --source=FILE` | Импортирует закреплённый архив прошивки по локальному пути |
| `fetch PROFILE --source=adb --serial SERIAL` | Читает файлы Android, объявленные в `original` файла `profile.json`, с физического автомобиля через авторизованный ADB; профиль со `status` `incomplete` читает их по `capture.json` |

До размещения `fetch` сверяет архив и файлы с размерами и SHA-256 из профиля. Каждая [страница профиля](../profiles/index.ru.md) называет свой способ импорта и имена штатных файлов. Архив импортирует сам лаунчер, а импорт с автомобиля использует закреплённый `adb` из SDK; оригиналы незавершённого профиля считываются инструментами Java, которые устанавливает `deps`.

В stderr `fetch` называет архив и его размер и показывает байты проверки архива, распаковки каждого образа Android и образов QNX, число файлов, извлечённых из каждого образа, и время импорта. Повторный `fetch` проверяет архив и сохранённые оригиналы и сообщает, что они уже импортированы. Если файла нет или у архива другой размер, ошибка называет ожидаемое обновление, а если размер совпадает с обновлением другого профиля, — этот профиль. Итог заканчивается следующей командой `voyemu build PROFILE`.

## build

`build PROFILE [MACHINE_PATH]` подготавливает новую машину, по умолчанию `machines/PROFILE`. Команда применяет [компоненты и рецепты](components.ru.md), собирает образы гостей, загружает гостей для проверки и последним записывает `runtime.json`. Если проверочная загрузка QNX не удалась, `build` завершает запущенные им процессы QEMU и графики и удаляет их RAM и копии образов. При успехе она выводит машину и путь к её `runtime.json`.

В образы гостей QNX входят двоичные файлы, собранные в CI. `build` скачивает их по пинам и проверяет, что штатные библиотеки профиля экспортируют всё, что эти файлы импортируют. Для Free 6.0.3 `build` записывает штатный скрипт запуска и `sysmgrtool` в секцию, которую для них резервирует библиотека front, — как данные, без компилятора. См. [рабочий процесс qnx-guest](../dev/ci.ru.md#рабочий-процесс-qnx-guest).

Подготовка устанавливает скрипты оболочки гостя QNX без комментариев, отступов, пробелов в конце строк и пустых строк, чтобы каждый поместился на место заменяемого штатного файла; в репозитории скрипты хранятся с ними. Скрипт гостя со встроенным документом (`<<`) подготовка отклоняет.

Нативные компоненты Android профиля тоже собираются в CI: `build` скачивает каждый по его пину и передаёт помощнику на Java; NDK не участвует. Библиотека, которая импортирует из библиотек образа Android, например библиотека нескольких дисплеев, компонуется с неразрешёнными импортами, и `build` проверяет, что библиотеки образа их экспортируют. См. [рабочий процесс android-native](../dev/ci.ru.md#рабочий-процесс-android-native).

Образ хоста QNX сохраняет штатные байты каждого неизменённого блока по 64 КиБ своего загрузочного потока; изменённые блоки Voyemu упаковывает сам, а на Free 6.0.3 подгоняет их размер так, чтобы запуск принял поток. См. [собственный упаковщик LZO1X](../why/lzo-packer.ru.md).

`--cluster=on|off` и `--multimedia=on|off` выбирают подсистемы; по умолчанию включены обе. `--cluster=off --multimedia=on` подготавливает только мультимедиа, а подготовку одной приборки Voyemu отклоняет до начала работы. Для профилей, которые это поддерживают, подготовка одного Android в существующую остановленную машину обновляет её систему Android и сохраняет записываемые диски и уже подготовленную приборку.

Новая подготовка отказывается писать в существующий каталог. Перед этапами, которые занимают диск, подготовка проверяет свободное место; инструментам, оригиналам, промежуточным файлам и записываемым дискам нужно намного больше места, чем один архив прошивки.

Профили с `qg-runtime` хранят состояние эмулируемой NVRAM в `/data/user_de/0/com.voyemu/nvram` внутри гостя. Первый вызывающий процесс атомарно создаёт этот файл из начальных данных `/system/etc/nvram` в системном разделе только для чтения. Затем штатные процессы работают с одним файлом; он переживает холодный старт в записываемом диске Android машины. Очистка данных Android-приложения `com.voyemu` удаляет это состояние, поэтому при следующем обращении файл снова создаётся из начальных данных.

## Подготовка без сети

`--offline` у `deps`, `fetch` и `build` использует только файлы, уже лежащие в корнях `.local`, и завершается ошибкой, если закреплённого входа нет. Успешная подготовка не доказывает, что работает каждое штатное приложение: это проверяет приёмка на запущенной машине.
