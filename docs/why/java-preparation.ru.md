# Подготовка на Java

## Решение

Подготовка APK, JAR и DEX и сбор оригиналов по `capture.json` работают на Java из `src/prepare/`. Пользователь не устанавливает JDK: CI собирает и публикует минимальную среду Java каждого хоста, помощник на Java и гостевой код Java профилей, а [`deps`](../how/preparation.ru.md#deps) их устанавливает. Код подготовки на хосте компилируется с `--release 25`; код, который работает внутри гостей Android, — с `--release 8` против пути классов (classpath) Android. Импорт архивов и всё остальное остаются в нативном CLI.

## Контекст

Адаптации Android декодируют, правят и заново кодируют код DEX и подписывают APK. Инструменты для этого — библиотеки Java: D8 и apksigner из Android Build Tools и dexlib2. Их версии закреплены в `src/prepare/libraries.json` и `src/prepare/toolchain.json`. Раньше подготовка компилировала свой помощник и гостевой код Java установленным JDK 25, который приходилось устанавливать каждому пользователю.

## Альтернативы

**Среда jlink и код Java, скомпилированный в CI.** jlink собирает из jmods закреплённого JDK только модули, которые использует помощник: `java.base`, `java.logging`, `java.net.http` и `jdk.unsupported`. Получается архив от 15 до 19 МБ на хост вместо JDK примерно на 300 МБ. Один исполнитель CI на Linux собирает все три хоста, а два прогона дают одни и те же байты. Помощник остаётся на той JVM, на которой его проверяли, поэтому его результаты побайтно не меняются. Нет только javac, поэтому помощник и весь гостевой код Java компилируются в CI.

**Образ помощника в GraalVM native-image.** Нативный помощник давал те же байты DEX, APK и JAR, но ему нужны метаданные отражения для dexlib2. Скорости JVM он достигает только с `-O3` под процессор сборки, а переносимая сборка x64 без инструкций SHA считала хеши примерно вдвое медленнее. Образ весит около 30 МБ в сжатом виде на хост, каждому хосту нужен свой исполнитель CI, а две сборки одного входа различались, так что пин мог бы называть лишь один результат CI.

**Переписать обработку DEX и APK на C++.** Слой DEX, запись с тем же байтовым результатом, что у dexlib2, рецепты и их тесты требуют в несколько раз больше работы, чем любой путь на Java, и рискуют изменить результаты, с которыми машины прошли приёмку.

**Конвейеры командной оболочки вокруг инструментов командной строки SDK.** Скрипты для каждого хоста, которые разбирают вывод инструментов и запускают процесс на каждый шаг.

## Аргумент

Вызов библиотек Java внутри процесса даёт проверкам `guard` и рецептам типизированный доступ к структурам DEX без разбора текстового вывода. Среда jlink оставляет этот код и его результаты прежними, воспроизводится, как остальные ресурсы CI, и не добавляет компилятора или метаданных, которые надо сопровождать. Код гостя с `--release 8` остаётся в пределах API Java самых старых гостей Android.

## Последствия

Для подготовки и запуска машины JDK не нужен. Рабочие процессы `java-runtime`, `java-helper` и `android-java` в [CI](../dev/ci.ru.md) собирают эти три ресурса, а правка исходника помощника или гостя требует нового ресурса; до публикации обновлённого ресурса разработчик явно выбирает сборку из исходников через `--jdk`. Без этой опции подготовка использует закреплённый ресурс помощника даже в рабочей копии исходников и сообщает `JAVA_HELPER_ASSET_MISSING`, если он недоступен. У разработчиков остаётся JDK 25 для тестов, проверок и рецептов. Код Java проходит проверки google-java-format, Checkstyle и Error Prone. Библиотеки и инструменты подчиняются [правилу пинов](pins.ru.md). Java покрывает и проверки разработчика, поэтому в репозитории [нет Python](no-python.ru.md). Страница [Компоненты и рецепты](../how/components.ru.md) описывает, что применяет подготовка.
