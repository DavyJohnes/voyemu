# Voyemu API через `voyemu test`

## Решение

Voyemu API работает по одному запросу JSON на процесс: `voyemu test --request FILE` или `-` для `stdin` читает запрос со `schema: 1` и пишет один ответ JSON в `stdout`, а диагностику — в `stderr`. Voyemu не запускает сетевую службу API и не реализует MCP.

## Контекст

Тестовые стенды, скрипты и агенты управляют сеансами: запускают машину, ждут экран, нажимают, читают дерево UI и делают снимки экранов. Сам сеанс живёт в супервизоре независимо от процесса клиента.

## Альтернативы

**Локальная сетевая служба.** Слушающему порту нужны аутентификация, управление временем жизни и защита от других локальных процессов.

**MCP.** Он привязывает интерфейс к одному протоколу агентов; клиент MCP может обернуть CLI.

**Клиентская библиотека для каждого языка.** Каждую библиотеку нужно написать, версионировать и публиковать отдельно.

## Аргумент

Любой язык, который умеет запустить процесс и прочитать JSON, может управлять Voyemu. У процесса на запрос нет состояния соединения, которое можно потерять: действие регистрируется до выполнения, его квитанция сохраняется, и аварийно завершившийся клиент позже читает результат через `operation.get`. Владение и исходы остаются в одном месте — в супервизоре — и следуют [правилу кодов ошибок](error-codes.ru.md).

## Последствия

Каждый запрос тратит время на запуск процесса. Коды завершения: `0` — успех, `3` — неподдерживаемая операция, `4` — отказ, тайм-аут или неудачный прогон. `info` перечисляет операции установленной версии. Кадры QNX — единственное потоковое исключение: они отдаются по gRPC на `127.0.0.1` с токеном для каждого поколения. Страница [Voyemu API](../how/api.ru.md) описывает запросы, владение и квитанции.
